## 二、缺陷清单

### 缺陷 1：用户详情/列表接口不返回角色字段

- **接口**：`GET /api/admin/users`（用户列表）、`GET /api/admin/users/{user_id}`（用户详情）
- **现状**：响应中**无 `roles` 字段**（用户属于哪些角色不可见）。
- **影响**：前端/测试无法确认用户被分配了哪些角色。
- **期望**：在用户详情、用户列表响应中补充 `roles`（角色ID列表或角色对象列表），例如：
  ```json
  {
    "user_id": 8,
    "roles": [{"role_id": 5, "role_name": "外部经纪人", "role_code": "external_broker"}]
  }
  ```

### 缺陷 2：`GET /api/admin/role/users` 参数解析失败（400）

- **接口**：`GET /api/admin/role/users?role_id=2`
- **现状**：返回 `{"code":1001,"message":"role_id: Input should be a valid integer, unable to parse string as an integer"}`。
  - 请求参数 `role_id` 值明明是整数 `2`，但后端将其解析为字符串后校验失败，属于 **FastAPI 参数类型声明/校验 bug**。
- **影响**：该接口疑似为「角色下用户列表」查询，但当前完全不可用。
- **期望**：修复后 `GET /api/admin/role/users?role_id=2` 应返回角色 2 下的用户列表。

## 三、建议新增接口

### 需求 1：查询「用户已分配的角色」列表
- **接口**：`GET /api/admin/users/{user_id}/roles`
- **入参**：`user_id`
- **返回**：该用户关联的角色数组（含 role_id / role_name / role_code）
- **用途**：验证单用户角色分配。

### 需求 2：查询「角色下的用户」列表
- **接口**：`GET /api/admin/role/{role_id}/users`（建议路径参数形式，规避缺陷 2 的 query 解析问题）
- **入参**：`role_id`
- **返回**：该角色下关联的用户数组（含 user_id / account / name）
- **用途**：按角色查看人员构成。

### 需求 3（推荐，最小改动）：用户接口补充 roles 字段
- 在 `GET /api/admin/users` 与 `GET /api/admin/users/{user_id}` 响应中增加 `roles` 字段，一次性解决「用户视角」的角色回读。

## 四、优化项（非阻断，建议完善）

### 优化 1：报备列表回填 customer_id 关联

- **接口**：`GET /api/sale/customer/report/list`
- **现状**：返回的报备记录中 `customer_id` 为 `null`（列表显示 `—`），但 `customer_name` / `mobile` 字段正常。
- **影响**：报备记录无法通过 customer_id 关联回客户主档，前端做跳转/关联展示不便。
- **期望**：报备列表中回填 `customer_id`（若后端存储了关联），或至少保证创建报备时持久化 customer_id。

### 优化 2：房源 total_price 未按建面×单价自动计算

- **接口**：`POST /api/sale/project/house/create`
- **现状**：创建房源时不传 `total_price`，返回的 `total_price` 为 `0`，未按「建筑面积 × 单价」自动计算。
- **示例**：1-1-101（89㎡ × 8800元/㎡ = 783200），但 total_price=0。
- **期望**：创建房源时若未传 total_price，后端自动按 `building_area × unit_price` 计算并落库；或前端显式传值。

### 优化 3：报备/到访链路未下发二维码（QR Code）数据

- **背景**：2026-08-11 到访确认流程中核对，报备 → 到访全链路接口返回**均无二维码字段**（qrcode_url / qrcode_content / qr_code 等）。
- **涉及接口**：`POST /api/sale/customer/report/create`、`GET /api/sale/customer/report/list`、`POST /api/sale/customer/visit/confirm/{report_id}`、`GET /api/sale/customer/visit/list`
- **现状**：仅返回 `report_id` / `report_no`（如 RP202608110001）与 `visit_id` / `visit_time`，无任何二维码能力。
- **业务价值**：房产分销场景通常需要：
  1. **报备二维码**：经纪人/渠道报备后生成专属二维码，客户到场扫码核销；
  2. **到访核销二维码**：到访确认后生成一次性核销码，验码确认；
  3. **渠道/经纪人专属推广码**：绑定渠道与客户推荐关系。
- **期望**：
  - 高优先级：报备创建 `report/create` 返回 `qrcode_content`（含 report_id/report_no 的编码串）或 `qrcode_url`；
  - 高优先级：到访确认 `visit/confirm` 返回一次性可过期核销二维码；
  - 中优先级：提供独立 `GET /api/sale/customer/report/{report_id}/qrcode` 二维码获取接口。

### 优化 4：到访记录未归属接待销售 / 客户未分配归属销售

- **背景**：2026-08-11 以置业顾问 lijie001(user_id=5) 确认到访（report_id=1，已传 receive_user_id=5）后核对，发现关联字段未落地。
- **涉及接口**：`POST /api/sale/customer/visit/confirm/{report_id}`、`GET /api/sale/customer/visit/list`、`GET /api/sale/customer/detail/{customer_id}`、`GET /api/sale/performance/personal`、`GET /api/sale/statistics/personal`
- **现状**：
  1. 到访列表 `visit.sale_user_id` 为 `null`（传了 receive_user_id=5 但未写入）；
  2. 客户详情 `customer.belong_sale_user_id` 为 `null`（客户未分配归属销售）；
  3. 个人业绩/统计 `visit_count=0`、`customer_count=0`（因关联缺失，统计不到今日到访）。
- **影响**：置业顾问无法在个人业绩/统计中看到自己的接待数据，影响业绩归属与提成计算。
- **期望**：
  1. 到访确认时 `receive_user_id` 应持久化到 `visit.sale_user_id`；
  2. 客户报备/到访后应回填 `customer.belong_sale_user_id`（归属接待销售）；
  3. 业绩/统计接口按归属关系正确汇总。

### 优化 5：认购接口字段与 ORM 模型不匹配（deposit_amount / discount_amount）

- **背景**：2026-08-11 认购录入（客户1认购3-2-301房源18）时发现。
- **涉及接口**：`POST /api/sale/transaction/subscribe/create`
- **现状**：传 `deposit_amount` 或 `discount_amount` 参数时，后端报 `'deposit_amount'/'discount_amount' is an invalid keyword argument for SaleSubscribe`（Pydantic 接口接收了字段，但 ORM 模型缺失）。
  - 带 deposit/discount 尝试均失败；仅传核心字段（customer_id/house_id/subscribe_amount/subscribe_date）可成功。
- **影响**：认购单无法录入定金与优惠金额，金额数据丢失（认购单只有 subscribe_amount）。
- **期望**：后端 `SaleSubscribe` 模型补充 `deposit_amount`、`discount_amount` 字段（或改名对齐），保证定金/优惠可正常落库。

### 优化 6：认购前需锁定房源（业务规则确认）

- **背景**：认购 house_id=18 时，未锁定房源直接认购报「房源状态异常，无法认购」；锁定房源后认购成功。
- **业务规则确认**：
  1. 认购前房源必须先锁定（`POST /api/sale/project/house/lock`，参数 house_id/customer_id/expire_minutes）；
  2. 锁定后房源 `house_status` 置为 `2`（已售）；
  3. 房源已有有效认购单后不可重复认购（报「该房源已有有效认购单」）。
- **建议**：技能/前端在认购流程中增加「先锁定房源」的前置引导，避免用户直接认购报错；同时确认锁定后 house_status=2 的语义是否合理（锁定应更接近状态3-锁定/4-预定，而非直接已售）。

### 优化 7：自定义时段统计接口 custom 单日查询数据全为 0

- **背景**：2026-08-11 以销售经理 liuyang001 登录，调用 `GET /api/sale/statistics/custom?project_id=1&start_date=2026-08-11&end_date=2026-08-11` 查询当日业绩，所有指标均为 0。
- **对比参考**：`GET /api/sale/statistics/overview/1` 的 `today` 块有正确数据（visit_count=1、contract_sets=1、contract_amount=818800）。
- **涉及接口**：`GET /api/sale/statistics/custom`
- **影响**：自定义时段统计功能异常，区间查询不准，报表维度不可用。
- **期望**：custom 接口单日查询结果应与 overview.today 一致，或给出明确日期格式/时区要求。

### 优化 8：统计接口未计入认购和回款（认购/回款维度缺失）

- **背景**：2026-08-11 实际发生：认购 1 套（818800元，SUB20260811000007）、回款 1 笔（240000元，PAY20260811000001）。
- **涉及接口**：`GET /api/sale/statistics/overview/{project_id}`、`GET /api/sale/statistics/personal`、`GET /api/sale/performance/personal`
- **现状**：overview.today 和 personal 统计中，subscribe_sets=0、subscribe_amount=0、payment_amount=0。
- **影响**：业绩看板只有签约维度，缺少认购和回款的实时统计，无法反映完整销售漏斗。
- **期望**：
  1. overview / personal / custom 统计接口补充认购和回款维度；
  2. 个人业绩 `total_paid_amount` 应按回款记录累计（当前全为 0）。

### 优化 9：个人业绩 customer_count 为 0（客户未归属销售）

- **背景**：yanjuxiu01（user_id=7）已签约 1 单（合同 CT20260811000001，sale_user_id=7），但 `GET /api/sale/performance/personal?user_id=7` 返回 customer_count=0。
- **根因关联**：与优化 4 同源——签约销售 ≠ 客户归属销售（customer.belong_sale_user_id 为 null），导致客户数统计不到。
- **影响**：个人业绩面板客户数始终为 0，不能反映销售员的客户保有量。
